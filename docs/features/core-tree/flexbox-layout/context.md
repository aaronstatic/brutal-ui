## Gotchas & Learnings

- **The fixture roots are absolute.** Each `flex_direction_*` fixture of `YGFlexDirectionTest` sets `position: absolute` on the root. The engine had no position type until phase 5. The root layout is the same (phase 5 confirms it in the Yoga source), so a port can keep or omit that line.
- **The engine resets X and Y of each child in step 3** (Yoga `setPosition`) on each full layout of the parent. Thus a second full layout does not convert a reverse offset two times. A measurement does not touch the positions.
- **A child on a stretch axis gets two calls.** Step 5 measures it (no layout), and step 7 lays it out with the cross size of the line. A child with a definite cross size gets its layout in step 5.
- **Self-check (phase 1 group 1).** A console program in the session scratch folder (outside the repository) ran the six fixtures `flex_direction_column_no_height`, `flex_direction_row_no_width`, `flex_direction_column`, `flex_direction_row`, `flex_direction_column_reverse`, and `flex_direction_row_reverse` through `LayoutEngine.Calculate` by reflection. All rects match the LTR half. A second pass gave the same rects. A nested row with a column-reverse child, an auto root with an available size, and a percent width also matched hand-computed Yoga values. After the pass, each element held no layout bit and kept the style and paint bits.

- **A deep percent chain asks for many different constraints (review group 1).** Each level measures its child one or more times with a size that the percent padding or maximum of the level changes, and then lays it out with another size. On a chain with alternate rows and columns, the count of different constraints at the leaf grows by about 1.7 times for each level. The owner size key removes the extra misses of the old reset, but it cannot remove this growth. See the allocation-guard follow-up.
- **The stack depth limit (review group 9, CR-10).** A scratch program (`cr10probe`, session scratch folder) lays out a plain column chain on a thread with a set stack size, with a binary search over child processes. On a 1 MB stack: 293 levels pass in Debug and 520 in Release. On an 8 MB stack: 2378 pass in Debug and 4219 in Release. Section 6 of the technical design says "keep the tree under 200 levels on a 1 MB stack". A stack overflow ends the process. The allocation-guard feature measures the Release limit again in its benchmark. The plan Notes item 13 ("about a thousand levels") stays as written.
- **Two justify fixtures need the pixel rounding (phase 3 group 1).** `justify_content_row_space_evenly` expects `root_child0` left 26 and `root_child2` left 77. The engine gives 25.5 and 76.5. `justify_content_min_width_with_padding_child_width_lower_than_parent` expects `root_child0_child0_child0` left 101. The engine gives 100.5. Yoga rounds these values to the pixel grid. The engine does not (Decision 5). Group 2 must skip the two fixtures with the reason "pixel rounding".
- **DONE in phase 6 (see "The loose percent measurement (phase 6)"). The loose percent measurement waits for phase 6 (phase 3 group 1).** `percent_within_flex_grow` (`YGPercentageTest`) and `rounding_inner_node_controversy_combined` (`YGRoundingTest`) fail. A child with a percent cross size in a container with no exact cross size gets the `Undefined` mode in Yoga (`isLoosePercentageMeasurement` in `distributeFreeSpaceSecondPass`). Thus the measured basis of the container is 0, not the full width. The `// Phase 6` marker in `DistributeFreeSpaceSecondPass` names this place.
